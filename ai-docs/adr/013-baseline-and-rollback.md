# ADR 013: W1은 시작 시점의 프로젝트 기준점을 기록하고, 변경 확인과 되돌리기를 그 기준점으로 계산한다

## 상태

Accepted — 2026-10-04

대체됨 — 2026-10-05. [ADR 019](./019-isolated-request-workspaces.md)의 작업 공간 격리로 대체한다. 이 ADR의 스냅샷 기법은
작업 공간의 시작점을 만드는 데 재사용한다. 아래는 대체 전 기록이다.

(이전 상태) 보류 — 2026-10-05. 기안 취소(되돌리기)는 W1 첫 출시 범위에서 뺀다. 되돌리기가 필요해지면 이 ADR의 기준점 방식 대신
Agent Orchestrator처럼 작업마다 Git branch/worktree에서 실행하고, 결재는 그 변경을 원래 폴더에 반영, 기안 취소는
branch를 버리는 방식으로 새 ADR을 쓴다(아래 "후속 방향").

기준점 생성과 복구 방식은 2026-10-04에 임시 Git 저장소에서 수동으로 검증했다(아래 "검증 기록").
`apps/server/src/project-baseline.ts`는 실행 흐름에 연결하지 않은 상태다.

## 맥락

W1([ADR 011](./011-target-user-and-w1.md))의 개발 단계는 사용자가 연결한 프로젝트 폴더의 파일을 직접
변경한다. 현재 앱은 실행 전 상태를 기록하지 않으므로 다음을 할 수 없다.

- 무엇이 바뀌었는지 사실로 보여주기([ADR 012](./012-evidence-based-state.md)의 변경 사실)
- 사용자가 결과를 받아들이지 않을 때 W1 시작 전 상태로 되돌리기

격리된 작업 공간(Git worktree)을 쓰면 두 문제를 함께 풀 수 있지만, 실행 경로 계약
([ADR 005](./005-explicit-workspace-scope.md))이 바뀌고, 승인 시 변경을 원래 폴더로 옮기는 과정이 추가된다.
W1에는 병렬 실행이 없으므로 격리는 아직 필요하지 않다.

또 비개발자의 프로젝트는 커밋되지 않은 변경이나 새 파일이 있는 상태일 수 있다. "깨끗한 상태에서만 시작"을
요구하면 비개발자가 스스로 해결할 수 없는 조건이 된다.

## 결정

### 1. 기준점

W1 Task의 첫 Run을 예약하기 직전, 연결된 프로젝트 폴더의 **현재 파일 상태 전체**를 기준점으로 기록한다.

- 범위: 커밋된 파일, 커밋되지 않은 수정, 아직 추적되지 않은 새 파일. `.gitignore` 대상은 제외한다.
- 기록 방식: 사용자의 Git index를 복사한 **임시 index**에 작업 폴더를 모두 추가하고 그 tree를 기록한다.
  사용자의 HEAD, branch, index(staged 상태), stash, 작업 파일은 바꾸지 않는다.
- 보존: tree가 Git 정리 과정에서 사라지지 않도록 `refs/pixel-office/baselines/<taskId>` 참조로 보존한다.
- 바이트 일치: 기준점 생성과 복구 모두 줄바꿈 변환을 끄고 실행한다(`core.autocrlf=false`). 변환이 켜져
  있으면 복구한 파일의 줄바꿈이 원본과 달라질 수 있다.
- 프로젝트 경로가 저장소 루트가 아니라 하위 폴더면 기준점과 변경 계산을 그 경로 범위로 제한한다.

### 2. 시작 조건

- 프로젝트 폴더가 Git 저장소 안에 있고 앱이 Git을 실행할 수 있어야 한다. 아니면 W1을 시작하지 않고,
  구현 용어 없이 이유를 안내한다(예: "이 폴더에서는 작업 전 상태를 기록할 수 없어 되돌리기를 보장할 수 없어요").
- 앱이 사용자 폴더에 저장소를 새로 만들지 않는다(`git init` 자동 실행 금지). 이 경우의 해결 흐름은 재검토
  조건으로 남긴다.
- 프로젝트당 열린 기준점은 하나다. 파일을 수정할 수 있는 다른 Task는 같은 프로젝트의 열린 기준점이 닫힐
  때(승인, 되돌리기, Task 삭제)까지 시작할 수 없다. 읽기 전용 Task는 영향을 받지 않는다. 동시 수정은 격리
  실행(로드맵의 Worktree / Parallel 단계)에서 다룬다.

### 3. 변경 사실

파일을 수정할 수 있는 단계가 끝날 때와 최종 검토 시점에 현재 상태를 같은 방식으로 기록하고 기준점과 비교한다.

- 결과: 추가 / 수정 / 삭제된 파일 목록과 patch.
- 저장: 목록은 앱 DB에, patch는 앱 데이터 폴더에 저장한다. 사용자 프로젝트에 쓰지 않는다.
- 마지막 Agent Run이 끝난 뒤 다시 기록한 상태가 그 Run 종료 시점과 다르면, 실행 밖에서 바뀐 파일(대개
  사용자의 직접 수정)로 표시한다.

### 4. 사용자 행동별 처리

| 행동      | 처리                                                                                                            |
| --------- | --------------------------------------------------------------------------------------------------------------- |
| 승인      | 변경을 그대로 둔다. 기준점 참조를 지우고 변경 사실 기록은 앱에 남긴다.                                          |
| 수정 요청 | 변경과 기준점을 그대로 둔다. 다시 진행한 결과도 같은 기준점(W1 시작 시점)과 비교한다. 자동으로 되돌리지 않는다. |
| 되돌리기  | 아래 5절                                                                                                        |
| Task 삭제 | 기준점 참조를 지운다. 파일은 바꾸지 않는다.                                                                     |

### 5. 되돌리기

- 실행 중인 Run이 없을 때만 가능하다. 실행 중이면 먼저 중단한다.
- 실행 전 확인 화면에 되돌릴 파일 수를 업무 언어로 보여준다("작업 시작 이후 바뀐 파일 8개를 작업 전 상태로
  되돌려요"). 실행 밖에서 바뀐 파일(3절)이 있으면 그 파일도 되돌려진다는 것을 따로 알린다. 파일 목록은
  "세부 정보"에서 본다.
- 기준점과 현재 상태의 차이에 있는 경로만 처리한다. 수정·삭제된 파일은 기준점 내용으로 복원하고, 기준점
  이후 새로 생긴 파일은 지운다. 차이 밖의 파일은 건드리지 않는다.
- 끝난 뒤 현재 상태를 다시 기록해 기준점과 같은지 확인한다. 다르면 성공으로 표시하지 않고 남은 차이를 보여준다.
- 성공하면 기준점을 닫고, Task는 같은 요청으로 다시 시작할 수 있는 상태가 된다. 정확한 상태 전이는 구현 시
  `task-state`의 전이 표와 함께 정한다.

`architecture.md`의 "정리 동작은 사용자가 연결한 Project 폴더의 원본 파일을 삭제하지 않는다"는 앱 데이터
정리에 대한 규칙이다. 되돌리기는 사용자가 명시적으로 요청한 복구이며, 이 ADR이 정한 범위(기준점 이후 바뀐
경로, 확인 후 실행)에서만 프로젝트 파일을 바꾼다.

### 6. 보장하지 않는 범위

되돌리기 화면과 문서에 다음을 숨기지 않는다.

- `.gitignore` 대상 파일: 설치된 의존성 폴더, build 결과물, 무시된 설정 파일 등은 기준점에 없으므로 복구되지
  않는다. 예를 들어 패키지 설치를 되돌리면 의존성 목록 파일은 복구되지만 설치된 폴더는 남는다. 이 이유로
  앞으로 작성할 Permission 번역 ADR에서 새 패키지 설치는 기본적으로 사용자에게 묻는 작업이어야 한다.
- 프로젝트 폴더 밖의 변경, 외부 서비스에 보낸 요청.
- `.gitattributes`의 변환 필터(`eol`, `filter`)가 있는 파일은 바이트 일치를 구현 시 다시 검증한다. 확인할 수
  없으면 5절의 사후 확인으로 차이를 보여준다.

### 7. 화면 용어

Simple Mode는 "작업 전 상태", "바뀐 파일", "되돌리기"만 쓴다. Git, commit, ref, tree 같은 용어는 Developer
Mode와 "세부 정보"에서만 보여준다(기준점 식별자, 참조 이름, patch).

## 검증 기록 (2026-10-04, 수동)

임시 저장소에 커밋된 파일 수정, staged 새 파일, 추적되지 않은 파일, 무시된 폴더를 만든 뒤 다음을 확인했다.

- 임시 index로 기준점을 만든 전후 `git status` 출력이 같다(staged 상태 포함). HEAD와 stash는 바뀌지 않는다.
- Agent 변경(수정, 새 파일, 추적되지 않은 파일 삭제, 무시된 폴더에 파일 추가) 후 기준점 대비 차이가
  `M` / `A` / `D`로 정확히 나온다. 무시된 폴더의 변경은 나오지 않는다.
- 복원과 삭제 후 `git status`가 시작 전과 같다. 무시된 폴더의 새 파일은 남는다(6절 한계).
- `core.autocrlf=true`에서 복원하면 LF 원본이 CRLF로 바뀐다. `core.autocrlf=false`로 기준점 생성과 복원을
  하면 LF와 CRLF 원본 모두 바이트 단위로 같게 복원된다.

## 후속 방향 (2026-10-05)

- W1 첫 출시에서는 결재 전 변경을 되돌리는 기능을 제공하지 않는다. 화면에서 "되돌리기"를 약속하지 않는다.
- 되돌리기를 제공할 때는 격리 실행(작업별 branch/worktree)을 기본으로 한다. 결재 = 변경 반영, 기안 취소 = branch 폐기.
  격리 실행은 실행 경로 계약(ADR 005)을 바꾸므로 새 ADR로 결정한다.
- 변경 사실(ADR 012) 수집은 격리 실행에서도 branch 간 비교로 같은 형태를 만들 수 있으므로 지금 방식에 묶지 않는다.

## 결과

- W1은 격리 실행 없이 변경 확인과 되돌리기를 제공한다. 실행 경로 계약(ADR 005)은 바뀌지 않는다.
- 같은 프로젝트에서 파일을 수정하는 일은 한 번에 하나만 진행된다. 이 제약은 화면에서 "같은 프로젝트에서
  진행 중인 작업이 끝나야 시작할 수 있어요"처럼 사유와 함께 보여준다.
- 사용자 저장소에 `refs/pixel-office/` 참조가 일시적으로 생긴다. 일반 push 설정에서는 원격으로 올라가지
  않지만, 모든 참조를 올리는 설정(`--mirror`)에서는 올라갈 수 있다. 기준점을 닫을 때 지운다.
- 큰 저장소에서는 기준점 기록에 시간이 걸릴 수 있다. 사용자의 index를 복사해 시작하므로 바뀌지 않은 파일은
  다시 읽지 않지만, 실제 소요 시간은 기준선 측정에서 확인한다.

## 재검토 조건

- 같은 프로젝트에서 여러 W1을 동시에 진행해야 할 때(격리 실행으로 대체 또는 확장)
- Git 저장소가 아닌 프로젝트 사용자가 W1의 주요 대상으로 확인될 때
- 기준점 기록 시간이 사용자가 기다릴 수 없는 수준으로 측정될 때
- 무시된 파일 변경 때문에 되돌리기 후에도 프로젝트가 동작하지 않는 사례가 반복될 때
