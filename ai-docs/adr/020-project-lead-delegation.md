# ADR 020: 여러 동료를 엮는 일은 프로젝트마다 있는 팀장에게 말해서 맡긴다

## 상태

Accepted — 2026-10-05

10절 1단계(옛 구조 제거)를 구현했다(2026-10-05): Workflow 단계 실행, preset, 단계 사이 메시지 전달과 받는 사람 선택, 팀 만들기·선택 화면을
걷어내고, 결과 형식은 기안서 필드(`Task.resultFormat`)로, Team 패키지의 순서는 `workflowGuides` 안내로 옮겼다.
10절 2·3단계를 구현했다(2026-10-05): 프로젝트 팀장 대화(`apps/server/src/lead/`, 읽기 전용 실행, 도구 권한 요청은 자동 거절),
계획서 보고(`report_result`의 `plan`)와 결재·반려, 결재 시 기안서 생성, 앞 기안 대기(`Task.waitsFor`, 순서 대기로 표시)와
자동 시작, 앞 기안 결과 전달, "내가 보고 넘김"(`Task.reviewBeforeNext`), 프로젝트 화면의 팀장 탭(슬라임 캐릭터, 받을 것 목록 계획서 카드).
남은 것은 4단계의 맡긴 기안 상태 보고 자동 기록, 계획서 완료 정리, 결재함·사이드바의 계획서 표시, 조직도의 팀장이다. 이 ADR은 1단계에서 만들 것(결정 1~8절)과, 1단계 결과를 보고 하나씩 붙일 가설(9절)을 나눈다.
진행 순서는 10절을 따른다.

## 맥락

지금은 여러 동료를 엮으려면 사용자가 "팀"(Workflow preset)을 미리 정한다. 라떼(UX) → 모카(UI) → 단풍(개발)처럼
단계 순서, 단계별 결과 형식, 파일 수정 여부, 중간 확인을 고르고, 새 요청에서 그 팀을 고른다. 이 방식에는 다음 문제가 있다.

- 팀을 만드는 곳이 시작 전 기안서의 준비 패널 안에 숨어 있다. 직접 만든 팀은 동료 순서만 저장되고 단계 설정은
  정할 수 없다.
- 일마다 필요한 동료와 순서가 다르다. 문구 하나 고치는 일에 세 단계를 다 거치거나, 사용자가 매번 단계를 골라야 한다.
  비개발자는 "어떤 순서로 누구에게 넘길지"를 미리 설계하기 어렵다.
- 한 기안서 안에 여러 단계가 들어 있어 단계 판단, 중간 확인, 단계별 반려, 단계 사이 메시지 전달 규칙이 모두 이 구조
  때문에 복잡해졌다.

Agent Orchestrator(AO, 2026-10-05 README·CLI 문서·공식 문서 확인)에는 팀이나 파이프라인을 설계하는 화면이 없다.

- 프로젝트마다 이어지는 오케스트레이터 Agent가 있다. 사용자가 원하는 결과를 말하면 저장소 맥락과 지금 상태(돌고 있는
  worker, PR, CI, 리뷰)를 보고 일을 나눠 worker를 띄우고, 필요한 맥락만 넘기고, worker의 보고
  (`ao report --done / --needs-input / --stuck`)를 받아 후속 작업을 조율한다. 직접 구현하지 않는다. 계획 결재 단계는 없다.
- 이름 붙은 에이전트가 없다. worker는 작업마다 harness(Claude Code, Codex 등)와 모델을 골라 새로 띄운다.
- 사용자가 에이전트나 스킬을 만들지 않는다. 전문성은 harness의 일반 능력, 저장소에 이미 있는 `AGENTS.md`·`CLAUDE.md`·
  `.agents/skills`, 오케스트레이터가 넘기는 맥락에서 온다. 대상이 저장소에 규칙을 써 두는 개발자이기 때문에 성립한다.

[ADR 016](./016-agent-operating-principles-from-ao.md) 원칙 8은 이를 "팀장 비서"로 옮기고 Phase 6으로 미뤘다.
이 ADR은 그 원칙을 앞당겨 고정 팀을 대체한다.

### 검토에서 확인한 위험

결정 전에 다음 위험을 검토했고, 1단계 범위와 9절의 가설 분리에 반영했다.

1. 비개발자는 분할이 맞는지 판단하기 어렵다. 계획서가 "누가 무엇을"만 보여주면 결재가 확인이 아니라 습관적인 도장이 된다.
2. 분할, 담당, 장비, 채용 판단이 모두 팀장 한 명의 LLM 판단에 걸린다. 고정 단계는 답답하지만 예측 가능했다.
3. 기안을 나누면 앞 담당의 판단 근거가 요약으로만 넘어가고 세션이 늘어 토큰이 더 든다.
4. 파일을 바꾸지 않는 기안(UX, UI 명세)은 결재 없이 끝나므로, 옛 엔진의 중간 확인에 해당하는 장치가 없으면 사람이 보기 전에
   구현이 시작된다.
5. 채용, 프리랜서, 장비, 스킬 층까지 한 번에 넣으면 비개발자가 배울 개념이 너무 많고, 어느 것이 효과가 있었는지 알 수 없다.
6. 동료 페르소나가 결과 품질을 올린다는 근거는 아직 없다(같은 모델에 지침과 스킬만 다르다). 채용 기능은 이 가정 위에 있다.

## 결정 (1단계)

### 1. 일을 맡기는 길은 둘이다

| 길              | 언제                                   | 결과                           |
| --------------- | -------------------------------------- | ------------------------------ |
| 새 요청         | 맡길 동료 한 명이 분명할 때(기본 길)   | 기안서 하나                    |
| 팀장에게 말하기 | 여러 동료가 나눠 해야 하거나 모호할 때 | 계획서 → 결재 → 기안서 여러 개 |

- 새 요청의 담당은 동료 한 명이다. 팀(고정 단계)을 고르는 선택지는 없다.
- 두 길로 만든 기안서는 같은 보드에 올라가고 같은 규칙([ADR 018](./018-request-run-rules.md), [ADR 019](./019-isolated-request-workspaces.md))으로 진행한다.
- 화면에 늘 보이는 개념은 팀장, 기안, 결재 셋으로 제한한다.

### 2. 팀장은 프로젝트마다 하나다

- 팀장은 동료(Agent)가 아니라 프로젝트의 역할이다. 동료 목록과 사원증 대상에는 들어가지 않지만, 조직도 맨 위와 프로젝트
  화면에 펫이 아닌 에이전트 모습의 캐릭터로 나온다.
- 팀장 대화는 프로젝트에 붙어 계속 이어진다. 목표, 결정, 제약, 앞서 맡긴 일을 기억한다(같은 runtime 세션을 이어가고,
  이어갈 수 없으면 앱이 남긴 계획서와 보고 기록으로 새 세션에 맥락을 넘긴다).
- 팀장은 프로젝트 메모, 확인 방법, 동료 목록(이름, 역할, 스킬, 권한), 진행 중인 기안서와 상태, Team 패키지의 일하는 순서
  안내를 보고 판단한다.
- 팀장은 직접 일하지 않는다. 파일 쓰기 권한 없이 실행하고, 프로젝트 폴더는 읽기만 한다.
- 팀장이 쓸 runtime과 모델은 프로젝트 설정에서 정한다. 기본값은 workspace 기본 동료의 runtime이다.
- 프로젝트 없이 대화에는 팀장이 없다.

### 3. 계획서는 "끝나면 무엇을 받는지"로 보여주고, 사람이 한 번 결재한다

- 팀장은 앱이 제공하는 보고 도구로 계획서를 올린다. Claude는 앱 내부 MCP 도구(`propose_plan`), 도구가 없는 runtime은
  정해진 형식의 응답 블록을 쓴다([ADR 016](./016-agent-operating-principles-from-ao.md) 원칙 2와 같은 방식).
- 계획서에는 기안마다 다음을 적는다.
  - 끝나면 받을 것(결과물을 업무 언어로: "로그인 화면 흐름 정리 문서", "실패 문구가 바뀐 로그인 화면")
  - 맡길 내용(그 동료에게 넘길 맥락)과 담당 동료(1단계에서는 있는 동료만)
  - 결과 형식(UX, UI, 개발 등 [ADR 012](./012-evidence-based-state.md) Output Contract)과 파일이 바뀌는지
  - 앞 기안(이 기안을 시작하기 전에 끝나야 하는 기안)
  - 내가 보고 넘김: 이 기안의 결과를 사람이 확인한 뒤에야 뒤 기안을 시작할지
- 계획서 전체에는 왜 이렇게 나눴는지 한두 문장과 대략의 규모(기안 수, 파일이 바뀌는 기안 수)를 적는다.
- 계획서는 팀장 대화 안에 결재 카드로 보인다. 사용자는 결재하거나 의견을 달아 반려한다. 반려하면 팀장이 의견을 반영해
  새 계획서를 올린다. 결재 전에는 아무 기안서도 만들지 않는다.
- AO는 계획 결재가 없지만, 비개발자가 무엇을 받게 되는지 한 번 보고 시작하게 하려고 결재를 둔다(ADR 016 원칙 4).

### 4. 앞 기안 관계로 진행한다

- 결재하면 앱이 기안서를 만든다. 앞 기안이 없는 기안서는 바로 시작한다.
- 앞 기안이 있는 기안서는 보드의 순서 대기 칸에서 기다린다(사유: "'흐름 정리'가 끝나기를 기다리는 중"). 앞 기안이 모두
  완료되면 앞 기안의 결과(요약과 Output Contract 결과)를 참고 자료로 받아 자동으로 시작한다.
- "내가 보고 넘김"인 기안은 파일이 바뀌지 않아도 결과 확인 대기로 멈추고, 사람이 확인해야 완료된다.
- 앞 기안이 실패하거나 취소되면 뒤 기안은 시작하지 않고 대기에 남는다.
- 같은 폴더를 쓰는 순서 대기(ADR 018 1절)와 같은 장치로 처리한다.

### 5. 팀장은 맡긴 일의 보고를 받는다

- 팀장이 맡긴 기안서가 결재 대기, 질문, 실패, 완료로 바뀌면 팀장 대화에 보고가 한 줄씩 쌓인다.
- 팀장은 사용자가 말을 걸 때 쌓인 보고를 함께 읽는다. 한 계획서의 기안이 모두 끝나면 팀장이 한 번 정리하고, 필요하면
  후속 계획서를 올린다. 후속 계획서도 결재해야 실행된다.
- 보고가 올 때마다 팀장을 실행하지 않는다(토큰). 사용자의 말과 계획서 완료 때만 실행한다.
- 진행 중인 기안서의 질문 답변, 결재, 반려, 취소는 사람이 기안서에서 직접 한다. 팀장이 대신하지 않는다. 진행 중인 기안을
  바꿔야 하면 팀장은 새 계획서로 제안한다.

### 6. 고정 팀(Workflow 단계)은 이전 호환 없이 교체한다

- 정식 사용자가 없으므로 호환 계층을 두지 않는다. Workflow 단계 실행, preset 저장, 단계 사이 메시지 전달과 받는 사람 선택,
  팀 만들기·선택 화면을 먼저 걷어내고 새 구조를 만든다. 남아 있는 단계형 기안서 데이터는 정리한다.
- 여러 단계가 필요한 일은 팀장이 기안 여러 개와 앞 기안 관계로 나눈다.
- Team 패키지([ADR 014](./014-native-skill-and-team-packages.md) 4절)는 동료 정의와 스킬을 묶는 단위로 남는다. 패키지의
  Workflow 정의는 실행 순서가 아니라 팀장이 읽는 "이 팀이 보통 일하는 순서" 안내가 된다.

### 7. 화면

- 프로젝트 화면의 첫 탭은 "팀장"이다. 대화, 결재를 기다리는 계획서, 쌓인 보고, 이 팀장이 맡긴 기안서 묶음을 본다.
  기존 탭(기안서 보드, 기록, 설정)은 그대로 둔다.
- 계획서 결재 카드는 기안을 "받을 것" 중심 카드로 나열하고, 앞 기안 관계를 순서로 보여준다
  ("흐름 정리 문서 → 화면 명세(내가 보고 넘김) → 바뀐 로그인 화면(파일 수정, 결재)").
- 결재함과 사이드바 프로젝트 줄에 결재를 기다리는 계획서를 표시한다.
- 화면 언어는 팀장, 계획서, 기안, 앞 기안이다. orchestrator, worker, spawn, DAG를 쓰지 않는다.

### 8. 기존 결정과의 관계

- [ADR 016](./016-agent-operating-principles-from-ao.md) 원칙 8의 적용 시점을 Phase 6에서 이 ADR로 앞당긴다.
- [ADR 011](./011-target-user-and-w1.md) W1 "화면 개선 요청"은 팀장이 UX → UI → 개발 기안 셋을 앞 기안 관계로 나누는 흐름이
  된다. "자동 계획"은 계획서 결재를 전제로 W1 범위 안으로 들어온다. "특정 단계로 수정 요청"은 그 기안서를 반려하는 것이다.
- [ADR 012](./012-evidence-based-state.md)의 단계 진행 규칙(자동 진행, 중간 확인)은 앞 기안 규칙과 "내가 보고 넘김"으로
  옮겨간다. 확인 실패를 같은 담당에게 한 번 되돌려 보내는 규칙과 결재 조건은 기안서마다 그대로 적용한다.
- [ADR 018](./018-request-run-rules.md) 2절(받는 사람과 지금 단계 기준 메시지 전달)은 단계형 기안서가 없어지므로 폐기한다.
  기안서의 받는 사람은 담당 한 명이다.

## 9. 1단계 결과를 보고 붙일 가설

각 가설은 앞 단계의 사용성 테스트 결과로 필요가 확인될 때 별도 결정으로 채택한다.

| 가설                   | 내용                                                                                                                            | 채택 조건                                                     |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| 이번 장비              | 동료는 그대로 두고, 그 기안에서만 runtime·모델·스킬을 바꾼다. 팀장이 계획서에서 제안하고 결재로 확인한다                        | 있는 동료의 기본 장비로 결과가 부족한 사례가 반복될 때        |
| 프리랜서               | 조직도에 남지 않고 장비(runtime·모델·스킬)만 들고 와서 기안 하나를 하고 떠나는 담당. 결과가 좋으면 "정규직으로 채용"으로 남긴다 | 맞는 동료가 없어 팀장이 억지로 배정하는 사례가 확인될 때      |
| 채용공고               | 계속 필요한 역할은 계획서에 채용공고(직무, 맡을 기안, 스킬, runtime, 권한, 이유)를 붙여 결재로 동료를 만든다                    | 같은 역할의 프리랜서가 반복될 때. 팀장은 있는 동료를 우선한다 |
| 스킬 3층               | 프로젝트 스킬(저장소의 스킬과 규칙, 그 프로젝트에서 누구나 씀) + 동료의 주특기 2~3개 + 이번 장비. ADR 014 개정                  | runtime이 실행마다 스킬 묶음 전달을 지원하는 것이 확인될 때   |
| 피드백에서 스킬 만들기 | 반복된 반려 의견을 팀장이 스킬 초안으로 정리해 제안한다. 범위(프로젝트, 전체), 중복 정리, 낡은 스킬 정리를 함께 둔다            | 같은 종류의 반려가 반복된다는 기록이 쌓일 때                  |

이 가설들은 "사용자가 에이전트와 스킬을 미리 구축한다"를 피하려는 방향이다. AO는 대상이 개발자라 저장소의 규칙으로 이 문제를
피하지만, 비개발자의 일에는 그런 규칙이 없으므로 "일하면서 쌓이는" 방식으로 풀어야 한다.

## 10. 진행 순서

1. 옛 구조 제거: Workflow 단계 실행, preset, 단계 사이 메시지 전달과 받는 사람 선택, 팀 만들기·선택 화면, 단계형 데이터 정리
2. 팀장과 계획서: 프로젝트 팀장 세션, 계획서 보고 도구와 응답 블록, 결재·반려, 결재 시 기안서 생성
3. 앞 기안: 앞 기안 대기와 자동 시작, 앞 기안 결과 전달, "내가 보고 넘김"
4. 보고와 화면: 팀장 대화의 보고, 계획서 완료 정리, 결재함과 사이드바의 계획서, 팀장 캐릭터
5. 사용성 테스트(`pixel-office-usability-team`): 비개발자가 계획서를 보고 받을 것을 예상하는지, 반려율, 결재까지 걸린 시간,
   분할이 쓸 만한지
6. 9절 가설을 테스트 결과에 따라 하나씩 결정

## 결과

- 사용자는 팀 구성을 설계하지 않는다. 동료를 두고, 프로젝트의 팀장에게 원하는 결과를 말한다.
- 기안서 하나는 동료 한 명의 일이 되어 상태, 결재, 반려가 단순해진다. 여러 동료의 일은 기안서 여러 개와 앞 기안 관계로
  보드에 그대로 드러난다.
- Task 데이터에 출처 계획서, 앞 기안 목록, "내가 보고 넘김"이 필요하다. 계획서는 결재 기록과 함께 저장한다.
- 앞 기안 결과 전달의 품질이 전체 결과를 좌우한다. 요약만이 아니라 Output Contract 결과를 그대로 넘긴다.

## 재검토 조건

- 사용성 테스트에서 비개발자가 계획서를 보고도 받을 것을 예상하지 못하거나, 결재를 읽지 않고 누를 때(계획서 형식 재설계)
- 팀장이 계획을 자주 잘못 나눠 반려가 반복될 때(팀 안내 보강, 또는 자주 쓰는 분할을 고정 안내로 제공)
- 작은 계획까지 결재가 번거롭다고 확인될 때(기안 하나짜리 계획은 결재 없이 실행하는 선택지 검토)
- 계획서 완료 때만 팀장을 실행하는 방식으로는 후속 조율이 늦을 때(보고 즉시 실행 검토)
