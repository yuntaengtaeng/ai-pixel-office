# ADR 017: 화면은 프로젝트를 중심으로 구성하고, 모든 기안서는 대화로 진행한다

## 상태

Accepted — 2026-10-05

부분 구현 — 서버의 프로젝트 설정 저장(메모, 확인 방법, 준비 명령, 가져올 파일)과 제안 API, 기안서 대화의 메시지 전달,
7절 1단계 화면(사이드바 프로젝트 묶음, 새 요청 입력창, 프로젝트 보드와 인스펙터, 받는 사람을 고르는 Task Detail 대화 화면,
결재와 "맞춰 달라고 하기"), 보드의 순서 대기 칸, 프로젝트 설정(일반, 메모, 확인 방법, 작업 공간 준비, 기본 담당, 화면 미리보기),
7절 2단계(프로젝트별로 묶은 기록, 교육 자료실의 쓰는 프로젝트)를 구현했다(2026-10-05).
화면 미리보기는 사용자가 실행해 둔 주소를 여는 링크이며, 작업 공간에서 고친 내용은 결재로 프로젝트 폴더에 반영된 뒤 보인다.

## 맥락

현재 화면에는 다음 문제가 있다.

- 사용자는 Task를 만들 때마다 작업 폴더를 고른다. "이 프로젝트 일은 여기서 한다"가 화면 구조로 드러나지 않는다.
- 메신저와 Task가 다른 메뉴다. 메신저는 Claude 앱, Codex 앱 사용자에게 같은 입력 경험을 주려고 만들었지만,
  실제로는 메신저에서 만든 대화도 Task다. 같은 것을 두 곳에서 다룬다.
- 같은 기안서가 오피스, 결재함, Task 목록에 서로 다른 모양으로 보인다.
- 기록, 교육 자료실, 프로젝트 화면이 각자 다른 배치를 쓴다.

Agent Orchestrator(AO)는 등록한 저장소를 프로젝트로 두고, 사이드바에서 프로젝트 아래에 그 프로젝트의
세션을 펼친다. 가운데는 상태별 보드, 세션을 고르면 인스펙터에서 대화, 바뀐 파일, 미리보기를 본다. 모든
세션은 대화이며, 저장소 없이 도는 세션도 있다. Pixel Office는 이 구조를 따르되 비개발자도 읽을 수 있는
말로 옮긴다([ADR 011](./011-target-user-and-w1.md), [ADR 016](./016-agent-operating-principles-from-ao.md)).

## 결정

### 1. 프로젝트는 작업 폴더 하나다

- 프로젝트 하나는 사용자가 연결한 폴더 하나다([ADR 005](./005-explicit-workspace-scope.md)). 웹 Admin, 사용자 앱,
  제공자 앱처럼 저장소가 셋이면 프로젝트도 셋이다.
- 사이드바의 "프로젝트" 묶음에 프로젝트를 나열한다. 프로젝트를 고르면 그 아래에 진행 중이거나 사람의 판단이
  필요한 기안서를 펼친다. 많으면 일부만 보이고 "더 보기"로 넘긴다. 완료된 기안서는 보드에서 본다.
- 폴더 없는 대화는 "프로젝트 없이 대화"로 프로젝트와 같은 줄에 둔다(AO의 프로젝트 없는 세션).

### 2. 프로젝트 화면

- 머리말에 작업 폴더를 항상 보인다. "이 프로젝트에 요청"은 폴더가 고정된 채로 시작한다.
- 탭은 기안서, 기록, 설정이다.
  - 기안서: 상태별 보드. 칸은 순서 대기, 진행 중, 내 답변 필요, 결재 대기, 완료다. 순서 대기는
    [ADR 018](./018-request-run-rules.md) 1절을 따른다.
  - 기록: 이 프로젝트에서 만든 문서.
  - 설정: 일반(이름, 폴더, 설명), 프로젝트 메모, 확인 방법, 기본 담당, 화면 미리보기.
- 프로젝트 메모는 사람이 아는 맥락만 적는다. 저장소의 `AGENTS.md`, `CLAUDE.md`는 runtime이 따로 읽으므로
  옮겨 적지 않는다.
- 확인 방법은 폴더의 `package.json` script에서 후보를 찾아 제안하고, 사용자가 고른 명령만 검증 사실로 센다
  ([ADR 012](./012-evidence-based-state.md) 5절).

### 3. 메신저 메뉴를 없애고 모든 기안서를 대화로 진행한다

- 별도 메신저 메뉴를 두지 않는다. 모든 기안서(Task)는 대화로 시작하고 대화로 이어진다.
- "새 요청"은 Claude 앱, Codex 앱과 같은 입력창이다. 입력창 아래에서 동료, 폴더, 첨부를 고른다.
  폴더를 고르지 않으면 "프로젝트 없이 대화"로 시작한다.
- 결재는 폴더를 골랐는지가 아니라 파일이 바뀌었는지로 정한다([ADR 018](./018-request-run-rules.md) 3절).
- 기존 메신저 대화는 "프로젝트 없이 대화" 또는 해당 프로젝트의 기안서로 보인다.

### 4. Task Detail은 대화 화면이다

- 가운데: 대화. 동료가 바뀌는 지점에 "전결 · 라떼 → 모카 (질문 없음, 결과 형식 통과)"처럼 단계 구분선을
  넣는다. 도구 사용은 "파일 3개 수정", "pnpm test 통과"처럼 한 줄로 접어 둔다.
- 아래: 입력창과 받는 사람 선택. 기본값은 팀이며 지금 단계 담당이 받는다. 전달 규칙은
  [ADR 018](./018-request-run-rules.md) 2절을 따르고, 입력창에서 미리 알린다("단풍 차례에 전달돼요").
- 오른쪽: 결재란, 단계 진행, 바뀐 파일, 확인 결과, 미리보기, 결재 / 반려 / 수정 요청.
  수정 요청에서는 어느 단계부터 다시 할지 고른다.
- 질문이나 권한 요청으로 멈추면 대화 맨 아래에 답변 카드를 고정한다.
- 보드나 결재함에서 카드를 고르면 오른쪽 인스펙터로 빠르게 보고, "대화 크게 보기"로 이 화면을 연다.

### 5. 화면마다 역할을 나눈다

| 화면   | 역할                                         |
| ------ | -------------------------------------------- |
| 오피스 | 팀이 지금 무엇을 하는지 한눈에 보는 첫 화면  |
| 결재함 | 모든 프로젝트에서 내 차례인 기안서만 모은 곳 |
| 보드   | 한 프로젝트의 모든 기안서                    |

- 세 화면은 같은 상태 이름, 색, 카드 문법을 쓴다. 결재함 카드에는 프로젝트 색을 붙인다.
- 결재함은 별도 규칙을 갖지 않고 "모든 프로젝트 보드에서 내 차례만 거른 목록"으로 계산한다.

### 6. 교육 자료실과 기록

- 교육 자료실: 스킬 id 목록과 상세 두 칸. 상세에서 `SKILL.md` 원문, 쓰는 동료, 쓰는 프로젝트를 보인다.
  출처(기본 제공, 팀 패키지, 내가 만듦)로 거른다([ADR 014](./014-native-skill-and-team-packages.md)).
- 기록: 프로젝트별로 묶은 목록과 읽기 화면 두 칸. 프로젝트 화면의 기록 탭에서도 같은 목록을 본다.

### 7. 진행 순서

1. W1이 지나가는 길: 사이드바 프로젝트 묶음, 새 요청 입력창, 프로젝트 보드와 인스펙터, Task Detail 대화 화면, 결재
2. 기록, 교육 자료실, 프로젝트 설정의 나머지 항목

## 결과

- [ADR 009](./009-ui-ux-information-architecture.md)의 사이드바 그룹에서 메신저가 빠지고 프로젝트 묶음이 생긴다.
  [ADR 015](./015-visual-language-graphite-approval-office.md) 6절의 메뉴 목록도 이 ADR을 따른다.
- 메신저 화면(`features/chat`)의 입력 경험은 새 요청 입력창과 Task Detail 입력창으로 옮겨간다.
- 프로젝트 설정의 확인 방법, 프로젝트 메모, 기본 담당은 Project 데이터에 새 필드로 저장한다.
- 같은 기안서를 그리는 카드와 상태 표시는 한 곳에서 계산해 세 화면이 함께 쓴다.

## 재검토 조건

- 사용성 검증에서 비개발자가 사이드바의 프로젝트 → 기안서 계층을 어렵다고 느낄 때
- 폴더 없이 쓰는 사용자가 주요 대상으로 확인되어 "프로젝트 없이 대화"가 첫 화면이 되어야 할 때
- 프로젝트 수나 기안서 수가 사이드바로 감당할 수 없을 만큼 많아질 때
