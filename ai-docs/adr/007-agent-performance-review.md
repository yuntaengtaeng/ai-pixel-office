# ADR 007: 인사평가는 활동 기록을 기반으로 한 AI 팀 회고로 제공한다

## 상태

Proposed — 2026-09-05

## 맥락

AI Pixel Office는 Agent를 단순한 실행 설정이 아니라 Skill을 조합해 함께 일하는 AI 팀원으로 표현한다.
사용자가 Agent와 Skill의 활동을 돌아보고 팀에 애착을 느낄 수 있도록 사이드바에 `인사평가` 기능을 제공할 수
있다.

현재 `AgentRun`은 실행 Agent, 상태, 소요 시간, 사용량과 결과를 기록하지만 실행 당시 실제로 적용된 Skill
목록은 독립된 이력으로 보존하지 않는다. 현재 Agent의 `skillIds`를 과거 Run에 역으로 적용하면 Agent의 Skill
구성이 변경된 뒤 과거 통계가 달라진다. 따라서 가장 많이 사용한 Skill, Skill별 성공률, Agent와 Skill 조합의
성과를 정확히 계산할 수 없다.

또한 사용 횟수나 처리 속도만으로 Agent의 품질을 판단하면 다음 문제가 생긴다.

- 어려운 작업을 맡은 Agent가 상대적으로 낮게 평가될 수 있다.
- 빠른 실행과 적은 토큰 사용이 좋은 결과를 의미하지 않을 수 있다.
- 사용자가 많이 호출한 Agent가 실제로 가장 높은 품질을 제공했다고 단정할 수 없다.
- 생성형 모델의 비결정성과 Runtime, 모델 버전, 프로젝트 환경 차이가 평가에 반영되지 않는다.
- 경쟁과 서열을 강조하면 협업을 관찰하는 제품 목적보다 점수 최적화를 유도할 수 있다.

## 결정

`인사평가`는 사람의 인사 고과를 모방한 절대 평가 시스템이 아니라 **활동 기록을 기반으로 한 AI 팀 회고와
사내 문화 콘텐츠**로 정의한다.

### 정보 구조

사이드바에는 사용자가 이해하기 쉬운 제품 명칭인 `인사평가`를 사용한다. 화면 안에서는 지표의 성격을
`AI 팀 활동 회고`로 설명하고, 실제 업무 품질을 단독으로 판단하는 지표가 아님을 명시한다.

초기 화면은 다음 정보를 제공한다.

- 기간 선택: 이번 주, 이번 달, 전체
- Agent별 담당 작업 수, 완료 작업 수, 완료율
- 성공, 실패, 취소, 재시도 현황
- 평균 처리 시간과 토큰 사용량
- 가장 많이 사용된 Agent와 Skill
- Agent별 가장 많이 사용한 Skill
- 이전 기간 대비 활동 변화
- 근거가 되는 Task와 Run으로 이동할 수 있는 링크

단순 순위 외에 Pixel Office의 성격을 살리는 회고 콘텐츠를 제공한다.

- 이달의 Agent
- 해결사상: 실패 또는 변경 요청 이후 완료한 활동
- 묵묵한 일꾼상: 완료 작업이 많은 활동
- 품질 수호자상: 리뷰와 테스트 성격의 Skill 활동
- 만능 재주꾼상: 다양한 Skill을 활용한 활동
- 외길 장인상: 특정 Skill을 집중적으로 활용한 활동
- 불사조상: 재시도 후 완료한 활동
- 환상의 짝꿍상: 연속 Workflow에서 함께 높은 완료율을 보인 Agent 조합

부정적인 지표는 벌점이나 낙인으로 표현하지 않는다. 개선 제안에는 반드시 근거가 된 기간과 Task 또는 Run을
함께 표시한다.

### 평가 원칙

- 사용 횟수와 품질을 동일하게 취급하지 않는다.
- 전체 Agent 간 절대 비교보다 Agent 자신의 이전 기간과의 변화를 우선한다.
- 종합 등급을 제공하더라도 활동량, 완수율, 신뢰도, 효율, 품질 신호를 분리해 표시한다.
- 사용자 승인, 변경 요청, 재작업과 리뷰 결과가 없으면 품질을 추정하지 않는다.
- 자동 생성된 총평과 추천에는 AI가 생성한 해석임을 표시한다.
- 통계에서 제외된 실행, 불완전한 데이터와 계산 기준을 사용자가 확인할 수 있게 한다.
- 모델이나 Runtime 차이를 무시한 직접 비교는 하지 않는다.

### 실행 시점 Skill 스냅샷

Skill 통계는 현재 Agent 설정이 아니라 Run이 생성될 때 확정된 Skill 집합을 사용한다. 구현 시 `AgentRun`과
Skill 사이에 실행 이력을 추가한다. 관계 테이블을 사용한다면 최소 계약은 다음과 같다.

```text
run_skills
├─ run_id
├─ skill_id
├─ skill_name_snapshot
├─ skill_version
└─ position
```

- `skill_id`는 현재 로컬 Skill과 연결하는 식별자다.
- `skill_name_snapshot`은 Skill의 이름이 변경되거나 삭제되어도 과거 표시를 유지한다.
- `skill_version`은 Package 기반 Skill이 도입되기 전까지 nullable일 수 있다.
- `position`은 Runtime 지침에 합성된 순서를 재현하기 위해 보존한다.
- Community Package가 도입되면 package ID, exact version과 provenance를 스냅샷 계약에 포함한다.
- 재시도, 계속하기, 변경 요청 실행은 각각 별도 Run으로 집계하되 동일 Task 계보를 함께 표시한다.

Run에 적용된 Skill이 없는 경우 빈 스냅샷을 정상 상태로 기록한다. 과거 데이터에 스냅샷이 없다면 Skill별
통계에서 제외하거나 `집계 불가`로 표시하며 현재 Agent 설정으로 소급 추정하지 않는다.

### 집계와 API 경계

통계 계산은 web renderer가 전체 Run을 내려받아 수행하지 않고 server의 조회 전용 집계 경계에서 수행한다.
집계 API는 workspace와 기간을 명시적으로 입력받고 다음 수준의 결과를 반환한다.

```text
ReviewSummary
├─ period
├─ teamTotals
├─ agentMetrics[]
├─ skillMetrics[]
├─ collaborationMetrics[]
└─ awards[]
```

원본 Run과 Task가 사실의 원천이며 평가 결과와 상은 파생 데이터다. 초기에는 요청 시 계산하고, 데이터가
커져 성능 문제가 확인될 때에만 집계 테이블이나 캐시를 추가한다.

### 시각화

초기 막대그래프는 `@ai-pixel-office/design-system`과 styled-components로 구현한다. 단순 순위와 비율을
표현하기 위해 별도 차트 라이브러리를 도입하지 않는다. 시계열 축, 복합 툴팁, 확대와 같은 요구가 생기면
접근성과 번들 크기를 검토한 별도 결정으로 차트 라이브러리를 도입한다.

색상만으로 값을 구분하지 않고 수치와 레이블을 함께 제공한다. 막대그래프는 키보드 및 스크린 리더에서 같은
정보를 읽을 수 있어야 한다.

## 단계적 제공

### Phase 1 — 활동 회고 MVP

- 실행 시점 Skill 스냅샷 저장
- 기간별 Agent와 Skill 활동 집계 API
- Agent 완료 작업, 실행 상태, 평균 시간과 사용량
- 가장 많이 사용된 Agent와 Skill 막대그래프
- 사실 기반 상 3개에서 5개
- Task와 Run 근거 링크

### Phase 2 — 품질과 성장

- 사용자 승인, 변경 요청, 재작업률 기반 품질 신호
- Agent 자신의 이전 기간 대비 변화
- 추천 Skill과 사용되지 않은 Skill 안내
- Agent별 한 줄 회고와 다음 기간 제안

### Phase 3 — 협업과 Community 연계

- Workflow 인계와 Agent 조합 분석
- Skill 버전별 성과 비교
- Community Skill의 사용 및 유지 여부 판단 보조
- 사용자 승인 기반 칭호, 승진과 1:1 면담 콘텐츠

## 결과

- 사용자는 AI 팀의 활동과 Skill 활용을 재미있는 방식으로 회고할 수 있다.
- Agent와 Skill 사용 이력이 Run 시점에 고정되어 설정 변경 후에도 과거 통계가 유지된다.
- Community 도입 후 Skill 버전과 provenance를 같은 이력 계약으로 확장할 수 있다.
- 활동량을 품질로 오인하지 않도록 지표와 해석의 경계가 명확해진다.
- 정확한 Skill 통계를 위해 Run 생성 경로, DB schema와 repository 변경이 필요하다.
- 품질 평가에는 사용자 피드백 데이터가 필요하므로 초기 MVP만으로 종합적인 성과 판단은 할 수 없다.

## 재검토 조건

- 인사평가 결과가 Agent 자동 선택이나 Workflow 라우팅 정책에 직접 사용되는 경우
- Agent 간 보상, 과금 또는 외부 인사 의사결정과 연결되는 경우
- Community 공개 프로필이나 제작자 평판 점수로 노출되는 경우
- 모델과 Runtime이 다른 Agent를 보정해 비교해야 하는 경우
- 데이터 규모로 인해 요청 시 집계가 사용자 경험을 저해하는 경우
- 사용자별 또는 조직별로 활동 기록의 보존 및 삭제 정책이 필요한 경우
