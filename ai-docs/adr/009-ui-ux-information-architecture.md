# ADR 009: 픽셀 오피스 UI/UX 정보 구조와 계층 정리

## 상태

Accepted — 2026-09-06

## 맥락

AI Pixel Office는 픽셀 오피스, 펫 캐릭터, 에이전트 작업 상태를 핵심 제품 경험으로 삼는다. 현재 Live Office는 차별화된 시각 언어를 갖고 있지만, 설정·기록·스킬·성과 화면은 일반적인 관리 콘솔처럼 보인다.

또한 최초 사용자가 AI 연결, 에이전트 생성, 작업 폴더 연결, 첫 작업 생성을 스스로 추론해야 한다. Today, Project, Chat, Office에 작업 생성 진입점이 나뉘어 있고 Task 상세에는 실행·결과·권한·개발자 정보가 한 화면에 섞여 있다.

UI/UX 리뷰에서 다음 문제가 공통으로 확인되었다.

- 화면마다 border, shadow, 색상과 카드 밀도가 달라 시각적 계층이 불명확하다.
- 모든 Sidebar 메뉴가 같은 위계로 보여 업무·팀·자료·관리 영역을 구분하기 어렵다.
- 설정 화면에서 필수 연결, 선택 기능(MCP), 고급 개발자 옵션의 중요도 차이가 약하다.
- 모바일 Chat에서 목록과 대화 상세의 전환 문맥이 약하다.
- 오피스는 보기에는 좋지만 클릭 가능한 대상과 상태 정보의 접근성이 낮다.
- 빈 상태와 비활성화 버튼이 왜 비어 있거나 실행할 수 없는지 충분히 설명하지 않는다.

## 결정

### 1. 최초 실행 흐름을 명시한다

Today 화면에 최초 1회 시작 체크리스트를 제공한다.

```text
AI 연결 → 첫 AI 동료 만들기 → 작업 폴더 연결 → 첫 작업 만들기
```

각 단계에는 현재 상태와 다음 화면으로 이동하는 CTA를 둔다.

### 2. 작업 생성 경험을 공통 Composer로 통합한다

Today, Project, Chat, Office의 작업 생성은 공통 Composer를 사용하고, 호출 위치에 따라 프로젝트·담당자·대화 context만 주입한다. 버튼 라벨과 필수 입력 검증도 동일한 어휘 체계를 사용한다.

### 3. Task 상세는 상태별 대표 액션 중심으로 단순화한다

실행, 입력 대기, 검토, 완료, 실패 상태에 하나의 대표 Primary Action을 제공한다. Workflow·Context·권한·개발자 정보는 접힌 보조 영역으로 이동하고 삭제는 별도의 Danger Zone으로 유지한다. 실행이 불가능한 경우에는 원인과 해결 방법을 버튼 근처에 표시한다.

### 4. UI 시각 언어를 역할 기반으로 제한한다

패널은 기본·강조·상태 패널로 제한하고 border와 shadow 단계를 고정한다. 일반 UI 색상은 design token을 사용하며, 픽셀 오피스 전용 색상은 `officeTheme` 경계 안에서 관리한다. 카드 안에 카드를 중첩하기보다 내부 항목은 divider list를 우선한다.

### 5. 정보 구조를 그룹화한다

Sidebar는 다음 그룹으로 구분한다.

```text
업무: 오늘, 메시지, 프로젝트
팀: 에이전트, 스킬
자료: 기록, 성과
관리: 설정
```

모바일에서는 동일한 8개 메뉴를 가로로 나열하지 않고 drawer 또는 bottom navigation을 사용한다.

### 6. 오피스는 브랜드 중심이면서 접근 가능한 작업 화면으로 만든다

첫 방문 hint, 상태 범례, 실행 중 작업 수를 제공한다. 캐릭터가 많아질 경우 필터나 확대를 제공하고, 캔버스 정보와 동일한 내용을 접근 가능한 작업 리스트로도 노출한다.

### 7. 설정과 빈 상태는 중요도와 다음 행동을 명시한다

설정은 필수 연결, 선택 기능, 고급 옵션을 시각적으로 분리한다. MCP에는 `선택 사항`을 표시하고 개발자 옵션은 기본 접힘으로 둔다. 모든 Empty State는 다음을 포함한다.

```text
왜 비어 있는가 → 지금 무엇을 할 수 있는가 → 누르면 어디로 가는가
```

### 8. 접근성과 모바일 문맥을 기본 계약으로 삼는다

모든 상호작용 요소는 키보드 focus ring, 충분한 터치 영역, 색상 외 상태 텍스트를 제공한다. 긴 텍스트의 전체 내용 접근 방법과 `prefers-reduced-motion`을 지원한다. 모바일 Chat은 목록과 상세를 별도 뷰처럼 전환하고 상세 상단에 뒤로가기를 둔다.

## 우선순위

### P0

1. 최초 실행 체크리스트
2. 실행 불가 원인 및 해결 안내
3. Task 상세 대표 액션 단순화
4. Settings 필수·선택·고급 계층화
5. Sidebar 그룹화

### P1

1. 공통 Task Composer
2. 모바일 Chat navigation
3. 공통 Empty State 표준화
4. 오피스 사용법과 상태 범례
5. 카드 중첩과 과도한 shadow 축소

### P2

1. Records 타임라인화
2. Performance에 펫·에이전트 활동 연결
3. 에이전트 생성 단계형 UX
4. 전체 화면 focus·reduced motion·긴 텍스트 점검

## 결과

픽셀 스타일을 모든 요소에 강제로 적용하지 않는다. 대신 Live Office의 캐릭터성과 작업 상태 메타포를 제품 전체의 정보 구조, CTA, 상태 표현에 연결한다. 새 화면이나 기능을 추가할 때는 위 결정과 우선순위를 기준으로 시각적 계층과 사용자 다음 행동을 검토한다.

# Claude Agent

UI 디자이너, UX 디자이너 역할을 맡은 Claude 에이전트 2명이 코드 없이 본 ADR 문서와 `design-system.md`, `frontend-structure.md`만 근거로 진행한 디자인 리뷰다.

## UI 디자이너 리뷰 (Claude Agent)

### 동의하는 결정

- **4번** "카드 안에 카드를 중첩하기보다 내부 항목은 divider list를 우선한다"는 옳은 방향이다. 화면마다 border/shadow/밀도가 다르다는 문제(맥락 항목1)를 실제로 줄이는 구체적 규칙이고, 우선순위 P1-5("카드 중첩과 과도한 shadow 축소")로도 연결되어 있어 실행 가능하다.
- **7번** Empty State의 "왜 비어 있는가 → 지금 무엇을 할 수 있는가 → 누르면 어디로 가는가" 3단 구조는 카피 라이팅 차원까지 구체적이라, 디자이너가 바로 컴포넌트 스펙으로 옮길 수 있는 드문 결정이다.

### 우려/보완이 필요한 지점

- **[4]** "패널은 기본·강조·상태 패널로 제한하고 border와 shadow 단계를 고정한다"는 방향만 있고 값이 없다. design-system.md의 `radius`/`shadow` 토큰이 이미 존재하는데 ADR은 이 세 패널 유형이 그 토큰 중 무엇을 쓰는지, "고정"이 몇 단계(1단? 3단?)인지 명시하지 않는다. 디자이너가 새 화면을 만들 때 "이건 기본 패널인가 강조 패널인가"를 판단할 기준(예: primary action 유무, 상태 변화 빈도)이 빠져 있어 결국 다시 감으로 정하게 된다.
- **[4]** "officeTheme 경계 안에서 관리"라는 표현이 색상 경계만 다룬다. design-system.md는 픽셀 캔버스/펫 팔레트를 "콘텐츠 데이터"로 명확히 분리했는데, ADR 6번이 말하는 "오피스는 브랜드 중심이면서 접근 가능"해야 한다는 요구와 충돌 지점 — 캐릭터 카드·칩처럼 오피스 전용 색이 이미 UI chrome에도 새어 있는 상태를 ADR이 인지하고 정리를 지시하는지 불명확하다. 이 두 팔레트가 한 화면(예: Office 사이드 패널에 상태 배지)에 공존할 때 어떤 게 이기는지 규칙이 없다.
- **[6]** "필터나 확대를 제공"만으로는 부족하다. 캐릭터 수가 늘어날 때 밀도(Z-index 겹침, 라벨 가독성)에 대한 타이포그래피/최소 hit target 기준이 없고, 접근 가능한 작업 리스트와 캔버스가 "동일한 내용"이라 했지만 그 리스트의 시각 언어가 오피스 톤(픽셀)인지 관리 콘솔 톤(flat)인지 정하지 않았다 — 이건 바로 이 ADR이 해결하려던 "톤 충돌" 문제 그 자체를 오피스 내부에서 재발시킬 소지가 있다.
- **[7]** "선택 사항" 배지, 접힘 상태만 규정하고 색상 강도(필수=brand, 선택=neutral 등)나 접힘/펼침 시 모션(애니메이션 톤)을 언급하지 않는다. 8번에서 `prefers-reduced-motion`을 다루지만 이건 접근성 계약이지 브랜드 모션 톤(픽셀 느낌의 즉각적 전환 vs 일반 UI의 ease 전환)에 대한 답은 아니다.
- 다크모드가 문서 전체에 언급이 없다. 4/6/7번 모두 색상 계층을 다루면서 라이트 모드만 전제한 것으로 보이는데, 픽셀 아트 팔레트는 다크 배경에서 채도/명도 재조정이 필수적이라 이 결정이 선언되지 않으면 나중에 재작업 비용이 크다.

### 추가 제안

- 패널 3유형(기본/강조/상태)에 대해 실제 시각 스펙(border-width, shadow depth, 배경 톤 매핑)을 별도 표나 Figma 토큰으로 부속 문서화할 것을 제안한다.
- 오피스 화면과 일반 화면이 한 레이아웃(예: 사이드바+오피스 캔버스) 안에 동시에 보이는 경우의 "톤 전환 경계선" 가이드(예: 캔버스 프레임에 border-radius/shadow로 명확한 컨테이너 경계를 준다)를 7번 항목 옆에 추가하면 좋겠다.
- P2에 다크모드/브랜드 확장 검토 항목을 넣어 결과 섹션의 "위 결정과 우선순위를 기준으로 검토한다"는 원칙이 실제로 다크모드까지 커버하도록 명시할 것을 제안한다.

### 신규 안건 제안 (UI 디자이너)

- **아이콘·일러스트 언어 정의**: 픽셀 캐릭터는 오피스에만 있고 나머지는 일반 UI인데, 지금은 아이콘이 각 화면마다 따로 그려진 느낌이라 "이 앱의 아이콘이 flat인지 pixel인지" 기준이 없다. 에이전트/스킬/작업 상태를 나타내는 아이콘 세트를 브랜드 톤 하나로 통일할 필요가 있다.
- **로딩·스켈레톤의 시각 표현**: 로컬 우선 앱 특성상 AI 응답 대기, 파일 인덱싱, 에이전트 작업 시작처럼 대기 시간이 잦다. 일반 스켈레톤 바를 쓸지, 픽셀 캐릭터가 "일하는 중" 모션으로 대기를 대신 표현할지 정해야 톤 충돌 없이 일관된 로딩 경험이 나온다.
- **알림/토스트 디자인 체계**: 백그라운드에서 여러 에이전트가 동시에 작업을 완료·실패하는 멀티 에이전트 앱 특성상, 토스트가 겹치거나 중요도 없이 동일하게 뜨면 사용자가 놓치기 쉽다. 우선순위별 토스트 스타일과 최대 동시 노출 개수, 오피스 화면에 떠 있을 때의 톤(캐릭터 말풍선 형태 차용 여부)을 논의해야 한다.
- **한/영 혼용 타이포그래피 대응**: 코드/터미널 출력, 에이전트 이름, 파일 경로 등 영문·모노스페이스 콘텐츠와 한글 UI 텍스트가 한 화면에 계속 섞인다. 폰트 페어링과 line-height 규칙이 없으면 한글 문단 사이 영문 토큰이 삐뚤어 보이는 문제가 이미 곳곳에서 재발할 소지가 있다.
- **재방문자를 위한 진행감/보상 표현**: 온보딩 체크리스트 이후 "매일 다시 켰을 때 무엇이 달라 보이는가"가 없다. 완료한 작업 누적, 펫 성장, 에이전트 숙련도 같은 진행 지표를 오피스 화면에 은은하게 노출하는 안이 로컬 우선 AI 팀 앱의 재방문 동기를 만드는 데 필요해 보인다.

## UX 디자이너 리뷰 (Claude Agent)

### 동의하는 결정

- 결정 1(최초 실행 체크리스트)은 문맥에서 짚은 "AI 연결, 에이전트 생성, 작업 폴더 연결, 첫 작업 생성을 스스로 추론"하는 문제를 정확히 겨냥한다. 4단계를 명시적 순서로 못박은 것도 좋다.
- 결정 3에서 "실행이 불가능한 경우에는 원인과 해결 방법을 버튼 근처에 표시한다"는 부분은 P0 2번과 짝을 이루며, 막연한 비활성화 버튼 문제를 실질적으로 해결한다.
- 결정 7의 Empty State 3단계(왜 비어 있는가 → 무엇을 할 수 있는가 → 어디로 가는가)는 구체적이고 재사용 가능한 카피 프레임이라 동의한다.

### 우려/보완이 필요한 지점

- **[결정 1]** 체크리스트가 "Today 화면"에 상시 노출되는지, 완료 후 사라지는지가 문서에 없다. 4단계를 모두 마친 재방문 사용자에게도 Today가 체크리스트로 시작되면 매번 "이미 끝난 일"을 다시 보여주는 셈이 되어 결정 5의 "업무: 오늘"이 관리 화면처럼 느껴질 위험이 있다. 완료 후 표시 방식(축소/제거/재노출 조건)을 명시해야 한다.
- **[결정 2]** "호출 위치에 따라 프로젝트·담당자·대화 context만 주입한다"는 문장은 Today/Project/Chat/Office 네 곳의 사용자 의도가 실제로는 다르다는 점을 가볍게 처리한다. 예를 들어 Chat에서 작업 생성은 "지금 나누는 대화의 연장"이라는 멘탈모델이고, Office에서의 작업 생성은 "저 캐릭터에게 시킨다"는 멘탈모델이다. 동일한 Composer UI와 "동일한 어휘 체계"를 쓰면 Office의 캐릭터 은유가 희석될 수 있다 — 결정 6에서 강조한 "캐릭터성"과 결정 2의 "통합된 어휘"가 충돌하는 지점이다.
- **[결정 3]** "하나의 대표 Primary Action"은 단일 작업·단일 승인자 시나리오에는 맞지만, 문맥에서 언급된 "권한" 요소가 다중 승인이 필요한 경우(예: 여러 단계 검토)를 어떻게 대표 액션 하나로 축약할지 언급이 없다. 검토 상태에서 "승인/거부" 외에 "재작업 요청" 같은 제3의 액션이 필요한 경우도 배제된 것으로 읽힌다. 최소한 "대표 액션이 여러 개 필요한 예외 상태를 어떻게 표시할지" 원칙 한 줄이 필요하다.
- **[결정 5]** "업무/팀/자료/관리" 그룹명 중 "자료"에 기록과 성과가 함께 묶인 것이 애매하다. "기록"은 과거 작성물(콘텐츠)이고 "성과"는 지표/분석인데, 사용자가 "자료"라는 이름에서 분석 대시보드를 떠올리긴 어렵다. 또한 "관리"에 설정만 단독으로 들어가는데 그룹이 1개 항목뿐이면 그룹화의 의미가 약해진다 — 향후 항목이 늘어날 계획이 없다면 "관리" 그룹 자체보다 설정을 최하단 개별 항목으로 두는 편이 더 직관적일 수 있다.
- **[결정 8]** "모바일 Chat은 목록과 상세를 별도 뷰처럼 전환"이라고만 명시되어 있고, Today/Project/Office 등 다른 화면의 모바일 문맥은 결정 5의 "drawer 또는 bottom navigation"에만 의존한다. Office처럼 캔버스 기반 화면이 모바일에서 어떻게 재구성되는지(줌/팬이 유지되는지, 결정 6의 "접근 가능한 작업 리스트"가 모바일 기본값이 되는지) 구체성이 없다.

### 추가 제안

- 체크리스트의 각 단계 완료 후 "지금 뭘 할 수 있는가"를 결정 7의 Empty State 문구 패턴과 통일해 재사용하면 학습 비용이 준다.
- 결정 2의 Composer에 "호출 위치별 최소 1개 차별 요소"(예: Office에서는 대상 캐릭터 아바타를 헤더에 고정)를 명시해 공통화와 맥락감 사이 균형을 문서에 남기길 제안한다.

### 신규 안건 제안 (UX 디자이너)

- **재방문 사용자의 "정상 상태" 홈 경험**: 최초 실행 체크리스트를 다 마친 사용자가 매일 여는 Today 화면이 지금은 정의되어 있지 않다. 온보딩 이후의 "오늘 뭘 봐야 하는가"를 별도로 설계하지 않으면 체크리스트 잔재나 빈 레이아웃만 남을 위험이 있다.
- **다중 에이전트/작업 동시 실행 시 우선순위·주의 환기 표현**: 로컬 팀 작업 공간 특성상 여러 에이전트가 병렬로 돌아갈 텐데, "지금 내가 먼저 봐야 할 것"을 어떻게 순서 매기고 시각적으로 드러낼지(예: 입력 대기 중인 작업이 완료된 작업보다 우선인지) 논의가 없다.
- **실패/오류 발생 시 복구 여정**: 단순히 실패 상태 표시를 넘어, 왜 실패했는지 원인 분류(권한 문제/네트워크/모델 오류/사용자 입력 문제)에 따라 사용자가 취할 다음 행동이 달라야 한다. 재시도, 수정 후 재실행, 담당자 변경 같은 복구 경로가 정리돼야 한다.
- **알림·백그라운드 실행 중 컨텍스트 전환**: 여러 작업을 동시에 돌리고 다른 화면(Chat, Office, Project)으로 이동한 사용자가 "무언가 끝났다/입력이 필요하다"를 어떻게 인지하고, 클릭했을 때 원래 문맥(어떤 작업, 어떤 에이전트, 어떤 대화)으로 정확히 복귀하는지가 정의돼야 한다. 데스크톱 앱 특성상 OS 알림/배지와의 연동도 검토 대상이다.
- **로컬 우선 환경에서의 협업·핸드오프 시나리오**: "로컬 우선"이라는 전제가 한 명의 사용자를 가정하는지, 아니면 팀원 간 워크스페이스 공유·인계(예: 다른 사람이 만든 에이전트/작업을 이어받기)를 지원하는지가 불명확하다. 협업이 목표에 있다면 소유권, 가시성, 변경 이력 표현을 별도 안건으로 다뤄야 한다.
