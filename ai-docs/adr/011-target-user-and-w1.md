# ADR 011: 대표 Workflow를 먼저 정의하고 필요한 Harness를 그 아래에 추가한다

## 상태

Accepted — 2026-10-04

미구현 — 실행 계획과 현재/목표 매핑은 `plan/pixel-office-direction.md`가 소유한다.

## 맥락

AI Pixel Office는 Claude와 Codex를 실행 엔진으로 삼아 AI 팀에게 일을 맡기는 로컬 우선 데스크톱
제품이다. 비슷한 제품인 Agent Orchestrator(AO)는 개발자를 대상으로 격리 실행, 계획 Agent, PR/CI 루프를
이미 제공한다.

이전 제품 방향 문서는 목표 사용자에 PM / PO / Designer를 포함하면서도, 로드맵은 Worktree → Evidence →
DAG → Orchestrator → PR/CI → 마지막에 Pixel UI 순서로 Harness의 기술 완성도를 높이는 순서였다. 이
순서대로 가면 비개발자가 체감하는 변화는 마지막 단계에야 나오고, 결과물은 "AO 수준의 개발자 도구에 Pixel
UI를 입힌 제품"이 되기 쉽다. AO가 이미 앞선 영역에서는 차별화하기도 어렵다.

Pixel Office가 차별화할 수 있는 지점은 사용자층(비개발자 포함)과 Mental Model(Team / Work / Office)이다.
이 차별점이 실제로 체감되려면 로드맵의 기준이 기술 기능이 아니라 사용자가 끝낼 수 있는 일이어야 한다.

## 결정

### 1. 목표 사용자

목표 사용자는 PM / PO / Designer / Developer다. 기본 사용자 경험(Simple Mode)은 개발 도구를 다뤄 본 적
없는 PM / PO / Designer가 혼자 끝낼 수 있어야 한다. Developer는 같은 화면에서 필요한 세부 정보까지 펼쳐 본다.

### 2. 제품 판단 기준

Pixel Office는 Harness를 먼저 만들고 사용자 경험을 나중에 입히지 않는다. 대표 Workflow를 먼저 정의하고,
그 Workflow를 완성하는 데 필요한 Harness 기능을 추가한다.

이 기준에서 다음 규칙이 나온다.

1. **대표 Workflow가 우선이다.** 새 기능은 현재 대표 Workflow를 완성하는 데 필요한지로 판단한다. 필요하지
   않으면 그 Workflow가 완성될 때까지 미룬다.
2. **완료는 사용자 경험으로 정의한다.** 각 단계의 완료 기준은 기술 기능 구현이 아니라 사용자가 무엇을 할 수
   있게 되었는지로 적는다. Harness, 사용자 화면, Office 표현은 같은 단계에서 함께 낸다.
3. **사람은 필요할 때만 부른다.** AI 팀은 근거로 판단할 수 있는 동안 스스로 진행하고, 사람의 판단이 필요한
   순간에만 사람에게 돌아온다. 판단 규칙은 [ADR 012](./012-evidence-based-state.md)가 소유한다.
4. **구현 용어를 기본 화면에 노출하지 않는다.** Simple Mode는 Git, branch, commit, worktree, CLI, token 같은
   구현 용어를 쓰지 않는다. 내부적으로 Git 등을 사용하는 것은 허용한다. Developer Mode와 "세부 정보"에서는
   원래 용어와 원시 정보를 보여준다.
5. **다음 대표 Workflow는 현재 대표 Workflow가 완성된 뒤 정의한다.** 동시에 여러 대표 Workflow를
   진행하지 않는다.

### 3. 첫 번째 대표 Workflow — W1 "화면 개선 요청"

> [ADR 020](./020-project-lead-delegation.md)에 따라 W1은 프로젝트 팀장이 UX → UI → 개발 기안 셋을 앞 기안 관계로 나누고,
> 사용자가 계획서를 한 번 결재하는 흐름으로 바뀐다. "특정 단계로 수정 요청"은 그 단계의 기안서를 반려하는 것이 된다.

```text
스크린샷 + 요청
→ Product Team 실행
→ UX 검토
→ UI 검토
→ 개발
→ Evidence 기반 결과 확인
→ 승인 / 특정 단계 수정 요청 / 되돌리기
```

**사용자 행동의 의미**

| 행동      | 의미                                                                                                    |
| --------- | ------------------------------------------------------------------------------------------------------- |
| 승인      | 현재 로컬 프로젝트의 변경 사항을 사용자가 받아들인다. 변경은 그대로 유지된다.                           |
| 수정 요청 | 사용자가 고른 단계(UX / UI / 개발)로 돌아가 그 단계부터 다시 진행한다.                                  |
| 되돌리기  | W1 시작 전 기준점으로 프로젝트를 복구한다. 방식은 [ADR 013](./013-baseline-and-rollback.md)이 소유한다. |

승인은 commit, push, PR을 의미하지 않는다. 이것들은 개발자 Workflow의 개념이며 W1의 기본 사용자 경험에
포함하지 않는다. 승인 화면에서도 이 용어로 설명하지 않는다.

**Product Team 준비**

W1을 처음 쓰는 사용자가 UX Designer, UI Designer, Developer를 하나씩 만들고 Skill과 Workflow를 연결하게
하지 않는다. "Product Team 사용하기" 한 번으로 세 동료와 W1 Workflow가 준비되어야 한다. 이 기능은 W1을
설정 없이 시작하게 하는 최소 범위로 만들고, 범용 팀 템플릿 시스템, Team Marketplace, Team Builder는 이
결정의 범위가 아니다.

**전제 조건**

- AI 런타임(Claude 또는 Codex) 하나 이상이 연결되어 있다.
- 사용자가 프로젝트 폴더를 명시적으로 연결했다([ADR 005](./005-explicit-workspace-scope.md)).
- 그 프로젝트가 [ADR 013](./013-baseline-and-rollback.md)의 기준점 조건을 만족한다. 만족하지 않으면 시작
  전에 이유와 해결 방법을 구현 용어 없이 안내한다.

**W1 범위 밖**: 병렬 실행, DAG Workflow, 자동 계획(Project Orchestrator), commit / PR / CI, 소프트웨어 외
Vertical, 범용 팀 템플릿.

### 4. W1 완료 조건

다음을 모두 만족하면 W1이 완성된 것이다.

1. 비개발자 사용자가 위 W1 흐름 전체를 **Terminal을 직접 사용하지 않고** 끝낼 수 있다. 앱 밖의 도구나
   개발자의 도움이 필요하지 않다. 이는 최초 1회 AI 런타임 로그인과 프로젝트 폴더 연결을 포함한다.
2. "Product Team 사용하기" 한 번 이후 추가 설정 없이 첫 W1 요청을 보낼 수 있다.
3. 단계 사이 진행은 [ADR 012](./012-evidence-based-state.md)의 규칙을 따른다. 사람의 판단이 필요한 경우에만
   Human Desk로 돌아오고, 그 외에는 자동으로 다음 단계로 넘어간다.
4. 결과 확인 화면에서 사용자가 무엇이 바뀌었고 무엇이 검증되었는지(또는 검증되지 않았는지)를 Evidence로
   확인할 수 있다.
5. 승인, 특정 단계로의 수정 요청, 되돌리기가 모두 동작한다. 되돌리기 후 프로젝트는 W1 시작 전 상태와 같다
   ([ADR 013](./013-baseline-and-rollback.md)의 보장 범위 안에서).
6. 진행 중 받는 질문과 권한 요청은 구현 용어 없이 업무 언어로 표시된다.

## 결과

- 로드맵의 각 단계는 W1 완성에 필요한 순서로 정렬된다. W1에 필요하지 않은 병렬 실행, DAG, 자동 계획,
  PR/CI는 W1 완성 이후로 미룬다.
- 같은 이유로 Permission 번역과 한도 상태가 Worktree보다 앞선다. 개발 단계에서 권한 요청은 반드시
  발생하므로, 이를 번역하지 않으면 비개발자가 W1을 끝낼 수 없다.
- 개발자에게 익숙한 Git 기반 흐름은 Developer Mode와 이후 Delivery 단계에서 제공한다.
- 비개발자가 끝낼 수 있는지가 단계 완료의 기준이 되므로, 사용성 검증(`pixel-office-usability-team`)이
  각 단계의 필수 검증이 된다.

## 재검토 조건

- 기준선 측정과 사용성 검증에서 W1의 대상 사용자가 실제로는 Developer에 가깝다고 확인될 때
- W1 완성 이후 다음 대표 Workflow를 정할 때(이 ADR에 W2를 추가하거나 새 ADR로 대체)
- 시작 전 조건(AI 런타임 연결, 프로젝트 연결) 자체가 비개발자에게 넘을 수 없는 장벽으로 확인될 때
