# ADR 006: 파편화된 세션 기록은 태그가 아니라 임베딩 기반 의미 검색으로 재구성한다

## 상태

Proposed — 2026-09-05

## 맥락

AI Pixel Office는 workspace 안에서 여러 project와 task에 걸쳐 대화를 이어간다. 사용자가 하나의
도메인(예: 결제 도메인)을 다룰 때도 그 조사, plan, 구현 내용은 서로 다른 project/task/run에
`agent_runs.request_text`, `agent_runs.result_json`, `.runtime-logs/*.jsonl`로 흩어져 저장된다
(대화 기록 저장 방식 자체는 이 ADR의 결정 대상이 아니다).

이 파편화 문제를 Obsidian의 그래프 뷰에서 착안해 시각화로 접근하는 방안을 검토했으나, 두 시스템은
관계의 성격이 다르다. Obsidian 그래프는 노트 사이의 자유 형식 링크가 만드는 예측 불가능한 구조
(클러스터, 허브, 고아 노트)를 드러내는 데 가치가 있다. 반면 AI Pixel Office의
workspace-project-task-agent-run 관계는 이미 외래키로 완전히 정해져 있어, 이를 그래프로 그려도
kanban/list/detail 뷰가 이미 보여주는 것과 다른 정보가 나오지 않는다. 이 프로젝트에서 실제로
없는 축은 관계 구조가 아니라 "같은 도메인/주제로 흩어진 기록을 모으는 것"이다.

이 축을 메우는 방법으로 두 가지를 검토했다.

- **수동 태그**: 사용자가 task에 태그를 직접 붙인다. 구현은 가장 단순하지만 사용자가 매 대화마다
  태깅해야 하며, 요청은 "쓸모없는 대화를 하더라도 자동으로 붙었으면 좋겠다"였다.
- **LLM 자동 태깅**: run 완료 시 저비용 모델로 태그 문자열을 추출한다. 완전 자동이지만 태그 어휘가
  매번 달라질 수 있어("결제" vs "payment" vs "정산") 검색 매칭이 깨지기 쉽다.
- **임베딩 기반 의미 검색**: 태그 없이 세션 내용을 벡터로 저장하고, 쿼리 시점에 검색어를 임베딩해
  코사인 유사도로 관련 세션을 가져온다. 태깅 비용이 없고, 무관한 대화는 애초에 유사도가 낮아
  자연히 걸러진다.

## 결정

세션 기록의 파편화 문제는 관계 그래프 시각화가 아니라 **임베딩 기반 의미 검색**으로 해결한다.

- 검색 단위는 `agent_runs` 행(`request_text` + `result_json`, 필요 시 `.runtime-logs/*.jsonl` 원문)이다.
  길이가 임베딩 모델의 토큰 제한을 넘으면 run 하나를 여러 chunk로 나눠 각각 벡터화한다.
- **백필(backfill)**: 기존에 쌓인 `agent_runs` 전체를 한 번 스캔해 임베딩하는 일회성 배치 스크립트로
  과거 기록도 소급 적용한다.
- **증분 처리**: 이후로는 run이 완료될 때(orchestrator의 완료 훅) 해당 run만 임베딩해 추가한다.
  매 실행마다 전체를 다시 긁지 않는다.
- 임베딩 벡터는 SQLite에 저장한다. row 수가 적을 때는 애플리케이션 레벨 코사인 유사도 계산으로
  충분하며, 규모가 커지면 `sqlite-vec` 확장 도입을 검토한다.
- 사용자에게는 "관계 그래프 탐색" UI 대신 "이 주제로 뭘 했었지?" 질의에 답하는 검색/필터 UI를
  우선 제공한다. 태그나 노드-엣지 그래프는 이 검색 결과를 보조로 시각화하는 선택적 레이어로만
  나중에 얹을 수 있다.
- 사용자가 장기 보관할 내용을 직접 다듬는 `기록실` Markdown은 세션 원문과 별도 원본으로 둔다.
  Markdown frontmatter의 `taskId`/`runId`는 명시적 연결이고, 임베딩이 제안한 유사 연결은 검색 결과의
  보조 관계로 취급한다. 향후 연결 보기에서는 두 관계를 같은 확정 링크처럼 표현하지 않는다.
- 기록실 문서가 Task에서 명시적으로 참고 대상으로 선택되면 `referenceTaskIds`에 관계를 저장하고 실행
  프롬프트에 포함한다. 이는 향후 임베딩이 제안할 자동 유사 관계와 구분하며, 가져온 문서 안의 문장은
  상위 지시가 아니라 인용된 참고 자료로 취급한다.

## 결과

- 사용자가 태그를 붙이지 않아도 도메인별로 흩어진 조사/plan/구현 기록을 검색으로 다시 모을 수 있다.
- 무관하거나 쓸모없는 대화는 유사도 계산에서 자연히 낮은 순위로 밀려나 별도 필터링 로직이 없어도
  된다.
- 임베딩 API 호출 비용과 레이트리밋을 백필 배치 크기 설계에서 고려해야 한다.
- 벡터 저장/검색 계층(컬럼 스키마, 유사도 계산 위치)을 구현 시점에 별도로 설계해야 한다.
- 관계 그래프 시각화(workspace-task-agent-run)는 이미 존재하는 FK 구조를 그대로 그리는 것뿐이라
  우선순위가 낮다고 판단했다. 다만 태그/도메인 축이 생기면 "태그-세션" 그래프처럼 의미 검색 결과를
  보여주는 보조 시각화로는 재검토할 수 있다.

## 재검토 조건

- 세션 규모가 커져 SQLite 애플리케이션 레벨 코사인 유사도 계산이 성능 병목이 되는 경우
  (`sqlite-vec` 등 벡터 인덱스 확장 도입을 검토)
- 임베딩 API 비용/레이트리밋이 백필 규모에서 실질적 제약이 되는 경우
- 의미 검색만으로 사용자가 원하는 회상 경험이 부족해 명시적 태그나 관계 그래프 UI가 실제로
  요청되는 경우
