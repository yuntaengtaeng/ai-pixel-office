# ADR 012: Task와 Workflow 단계의 상태는 관찰 가능한 사실로 계산한다

## 상태

Accepted — 2026-10-04

구현 — 단계 결과 수집(보고 도구, 결과 블록), 검증 사실 분류, 단계 진행 규칙을 서버에 구현했다(2026-10-05).
화면의 근거 표시(바뀐 파일, 확인 결과)는 아직이다. 아래 "현재 동작"은 구현 전 기록이다.

## 맥락

현재 Task 결과는 Agent가 마지막 응답에 쓴 요약문(`TaskResult.summary`)이 중심이다. 순차 Workflow는 한
단계의 Run이 끝나면 산출물을 확인하지 않고 다음 단계를 시작하며, 마지막 단계가 끝나면 근거와 무관하게
Task를 `needs_review`로 전이한다. 이 구조에서는 다음 문제가 생긴다.

- Agent가 "테스트를 통과했다"고 쓰면 실제로 실행했는지와 관계없이 사용자는 그 말을 믿을 수밖에 없다.
- UX 단계가 사용자만 답할 수 있는 질문을 남겨도 UI와 개발 단계가 그 질문을 추측으로 채우며 진행한다.
- 사용자가 결과를 받았을 때 무엇이 바뀌었고 무엇이 검증되었는지 확인할 근거가 없다.

반대로 모든 단계 사이에 사람의 승인을 넣으면 W1([ADR 011](./011-target-user-and-w1.md))은 승인 목록을
처리하는 일이 되고, AI 팀에게 일을 맡기는 의미가 사라진다.

Agent Orchestrator는 칸반 상태를 session, PR, CI, review 사실에서 계산한다. Pixel Office도 같은 원칙을
따르되, 사실의 종류를 W1에 맞게 정의하고 업무 언어로 보여준다.

## 결정

### 1. Agent의 자기 보고는 상태의 근거가 아니다

> Agent가 완료했다고 말함 ≠ 완료

Agent의 요약문은 사용자에게 설명으로 보여줄 수 있지만, 상태 전이, 단계 진행, 검증 여부 판단의 근거로
쓰지 않는다. 예를 들어 요약문에 "테스트 통과"가 있어도 검증 사실이 없으면 화면은 "검증 없음"으로 표시한다.

### 2. 상태의 근거가 되는 사실

| 종류        | 사실                                                             | 수집 위치                                 |
| ----------- | ---------------------------------------------------------------- | ----------------------------------------- |
| 실행        | Run 종료 상태, 실패 사유, 사용한 도구, 소요 시간, 세션 한도 도달 | 정규화된 runtime event (**현재**)         |
| 산출물      | 단계별 Output Contract(아래 3절), 첨부, 생성 파일                | Orchestrator가 단계 종료 시 수집          |
| 변경        | 기준점 대비 변경된 파일 목록과 diff                              | [ADR 013](./013-baseline-and-rollback.md) |
| 검증        | 실행한 검증 명령, 종료 코드, 출력 위치                           | 도구 실행 event에서 분류                  |
| 사람의 판단 | 질문 답변, 권한 허용·거부, 승인, 수정 요청, 되돌리기             | Review / activity 기록 (**일부 현재**)    |

근거가 없는 항목은 숨기지 않고 비어 있음을 표시한다. "검증 없음"은 실패가 아니라 사실이다.

### 3. 단계 Output Contract

각 Workflow 단계는 끝날 때 정해진 형식의 산출물을 낸다. W1의 필수 필드는
`ai-docs/pixel-office-product-team/instructions/handoff-contract.md`의 Handoff contract v1을 따르고,
다음 한 가지를 더한다.

- `user_questions`: **사용자만 답할 수 있는** 질문. 다음 역할이 결정할 질문은 기존 `open_questions`에 남긴다.
  두 필드를 나누지 않으면 UX가 UI에게 넘기는 정상적인 미결정 사항도 사람을 부르게 된다.

| 단계 | 필수 필드                                           |
| ---- | --------------------------------------------------- |
| UX   | Handoff v1 UX 필드 + `user_questions`               |
| UI   | Handoff v1 UI 필드 + `user_questions`               |
| 개발 | Handoff v1 Developer result 필드 + `user_questions` |

- Output Contract는 앱 데이터로 저장하고 사용자 프로젝트 파일로 쓰지 않는다. 프로젝트에 쓰면 변경 사실과
  되돌리기 대상([ADR 013](./013-baseline-and-rollback.md))에 섞인다.
- 수집은 앱이 제공하는 **보고 도구**(단계 결과 제출, 사용자 질문, 막힘 보고)를 우선한다
  ([ADR 016](./016-agent-operating-principles-from-ao.md) 원칙 2). runtime의 구조화 출력 기능이나 마지막 응답의
  정해진 블록 해석은 보조 수단이다. 각 방법은 runtime별 실제 지원 여부를 확인해 adapter가 정규화하며, 지원하지
  않는 기능을 지원하는 것처럼 꾸미지 않는다.
- runtime별 수집 방법(2026-10-05 확인):
  - Claude Agent SDK(0.3.263): `createSdkMcpServer`와 `tool`로 실행 단위 보고 도구를 붙인다.
  - Codex app-server(codex-cli 0.159.2): 앱이 정의한 도구(`dynamicTools`)는 실험 API(initialize의
    `experimentalApi`)에서만 제공된다. 안정 API가 될 때까지 마지막 응답의 `pixel-office-result` 블록을 읽는다.

### 4. 단계 진행 규칙 — 사람은 필요할 때만 부른다

단계의 Run이 끝나면 Orchestrator는 다음 순서로 판단하고 처음 해당하는 규칙을 적용한다.

| 순서 | 조건(사실)                                      | 결과                                                                                   | Human Desk 항목                               |
| ---- | ----------------------------------------------- | -------------------------------------------------------------------------------------- | --------------------------------------------- |
| 1    | Run이 정상 완료되지 않음(실패, 취소, 세션 한도) | 해당 단계에서 정지                                                                     | 실패하여 판단 필요                            |
| 2    | Output Contract가 없거나 필수 필드가 빠짐       | 해당 단계에서 정지                                                                     | 실패하여 판단 필요(결과가 불완전함)           |
| 3    | `user_questions`가 비어 있지 않음               | 해당 단계에서 정지                                                                     | 추가 정보 필요                                |
| 4    | 검증 명령을 실행했고 하나라도 실패              | 같은 담당에게 실패 근거와 함께 **한 번** 되돌려 보냄. 다시 실패하면 해당 단계에서 정지 | 두 번째 실패 시 실패하여 판단 필요(확인 실패) |
| 5    | 사용자가 이 단계 뒤 확인을 요청해 둠            | 다음 단계 전에 정지                                                                    | 검토 필요(중간 확인)                          |
| 6    | 마지막 단계                                     | 최종 검토로 전이                                                                       | 검토 필요                                     |
| 7    | 그 외                                           | **다음 단계를 자동으로 시작**                                                          | 없음                                          |

- Run **도중** 권한 요청은 위 규칙과 별개로 즉시 Human Desk의 "승인 필요"로 간다. 업무 언어 번역과 자동
  승인 정책은 별도 ADR(Permission 번역)이 소유한다.
- 3번 질문에 사용자가 답하면 **같은 단계**를 이어서 진행하고, 끝나면 다시 이 규칙으로 판단한다.
- 검증 명령을 실행하지 않은 것은 정지 사유가 아니다. 최종 검토에서 "검증 없음"으로 표시하고 승인 전에 알린다.
- 중간 확인(5번)은 기본값이 아니다. 사용자가 요청할 때 단계 단위로 켠다.
- 4번의 자동 되돌려 보내기는 [ADR 016](./016-agent-operating-principles-from-ao.md) 원칙 3에 따른 개정이다
  (2026-10-04). 기계가 판단할 수 있는 실패는 먼저 담당에게 돌려보내고, 한도(1회)를 넘으면 사람에게 올린다.
- 그 밖의 자동 재시도(2번 결과 불완전 등)는 포함하지 않는다. 기준선 측정에서 잦고 반복 가능한 원인으로
  확인되면 별도로 추가한다.

### 5. 검증 사실의 분류

- 프로젝트가 정의한 확인 명령(예: `package.json`의 typecheck / test / build / lint script)을 실행한
  도구 event를 검증 사실로 기록한다. 기록 항목은 명령, 종료 코드, 소속 Run, 출력 위치다.
- 분류 규칙에 해당하지 않는 명령은 검증 사실로 세지 않는다. 분류할 수 없는 것을 검증으로 표시하지 않는다.

### 6. 기존 Task 상태와의 대응

W1에서는 Task 상태 종류를 늘리지 않고, 정지 사유를 별도 사실로 기록한다.

| 정지 사유              | Task 상태              |
| ---------------------- | ---------------------- |
| 권한 요청, 사용자 질문 | `needs_input`          |
| 결과 불완전, 확인 실패 | `blocked`              |
| Run 실패               | `failed` (현재와 같음) |
| 세션 한도              | 현재 처리 유지         |
| 중간 확인, 최종 검토   | `needs_review`         |

중간 확인에서의 "계속"과 최종 검토의 "승인"은 서로 다른 행동이다. 중간 확인의 계속은 Task를 `done`으로
만들지 않고 다음 단계를 시작한다.

### 7. 진행 표시

진행 정도는 %로 표시하지 않는다. 단계 사실로 `UI 명세 완료 · 2/3 단계`, 정지 사유로
`개발 완료 → 검토 필요`, `확인 실패 → 판단 필요`처럼 표시한다.

## 현재 동작

- 단계 Run이 완료되면 산출물 확인 없이 다음 단계를 시작한다(`Orchestrator.finishCompleted`).
- 이전 단계 결과는 요약문으로만 다음 단계에 전달한다.
- 결과는 요약문과 runtime artifact event, 요약문에서 추출한 로컬 파일 경로로 구성한다.
- 검증 명령과 변경 파일은 수집하지 않는다.
- 권한 요청은 `needs_input`으로 전이한다(이 결정과 같음).

## 결과

- Human Desk는 단순 승인 목록이 아니라 AI 팀이 스스로 진행하다 사람의 판단이 필요해진 일만 모이는 곳이 된다.
- Workflow preset은 Agent 순서만이 아니라 단계별 Output Contract와 파일 수정 허용 여부를 함께 가져야 한다
  (`plan/plan.md` §4.8.1의 단계 계약과 같은 방향).
- Agent 지침은 Output Contract 형식과 `user_questions` / `open_questions`의 구분을 알려야 한다.
- 근거 없는 "완료"를 보여주지 않으므로, 초기에는 "검증 없음" 표시가 자주 보일 수 있다. 이는 숨기지 않는다.

## 재검토 조건

- 기준선 측정이나 사용성 검증에서 사람을 부르는 횟수가 너무 많거나(불필요한 정지), 사람이 봐야 했던
  문제가 자동 진행으로 지나간 사례가 확인될 때
- runtime이 구조화 출력을 안정적으로 지원하거나 지원을 중단해 수집 방법을 바꿔야 할 때
- 소프트웨어 외 Vertical을 추가해 다른 종류의 사실을 정의해야 할 때
